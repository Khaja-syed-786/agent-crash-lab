# Release process

This experimental research lab is MIT licensed (see [LICENSE](../LICENSE)). Node.js 22 and 24 are supported and tested; no dependencies, custom secrets, Ollama or inference are required for CI/releases. This preparation does not create a tag or release. The release workflow has not yet been exercised by a real version tag.

## Future maintainer steps

1. Review privacy/licensing and sanitized findings. Run npm test, review the final diff, merge normally through a PR, and confirm main CI passes. Raw results, prompts/output reports, credentials and model files must never enter Git. Ignore rules are not a substitute for checking tracked history.
2. Choose a new supported tag: vMAJOR.MINOR.PATCH, optionally with SemVer prerelease identifiers and build metadata, up to 200 characters. Core numbers have no leading zeros; numeric prerelease identifiers have no leading zeros. Examples: v0.1.0, v0.2.0-rc.1, v0.2.0+build.1. Validate without side effects: `node scripts/release-tag.js v0.2.0-rc.1`. Prerelease labels, not build metadata, determine prerelease status. Coordinate the package version/documentation before tagging.
3. Only with authorization to publish a release, create a new tag on a reviewed commit already contained in origin/main and push that tag normally. Never move/force-push published tags. No tag is created by these instructions alone.
4. The single Release workflow triggers on v* tag pushes. It rejects unsupported syntax, checks full-history main ancestry, then runs npm test on both Node 22 and 24. A separate release job depends on all checks, rechecks ancestry/tag identity and uses GitHub CLI with --verify-tag and --generate-notes. Prerelease versions use --prerelease. No manual dispatch, downloads, inference, deployment or hosting is configured.
5. Inspect the workflow and generated notes. A failed job produces no new release; investigate rather than moving the tag. Existing releases are not overwritten automatically. GitHub-generated notes derive from repository PRs/history, which must remain sanitized.

Default workflow permissions are contents:read; only the release job has contents:write. Actions are pinned to full SHAs, credentials are not persisted by checkout, and all jobs have five-minute timeouts. Existing PR/main Node 22/24 CI remains separate and unchanged. Release workflow creates notes only: no asset upload, results/, credentials or model files. GitHub supplies source archives from the tag's tracked tree, so the tracked-tree/history privacy review is essential. No guarantee is made that a pattern scan detects every secret or ownership issue. Third-party runtime/model licensing is separate: neither Ollama nor model weights are redistributed in this repository.

Preparation checks: strict tag-parser regressions and the full scripted/mocked suite pass; actionlint 1.7.12 validates both workflows. Shellcheck/pyflakes were unavailable for the local lint pass. The tag-triggered path still requires a future authorized tag to verify actual GitHub Release creation. Standard MIT text follows the [Open Source Initiative template](https://opensource.org/license/mit); release creation uses the [GitHub CLI](https://cli.github.com/manual/gh_release_create). No vendored third-party code, npm dependencies or existing third-party license notices were found in the inspected repository. Runtime/model distributions are external and retain their own licenses. This inspection cannot establish the provenance of every original line.
